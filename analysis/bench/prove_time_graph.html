VerInf · Ligero prover · cost model

What determines proving time — as a graph

Every knob (model shape, Ligero parameters, s/R quantization) flows through derived quantities into five cost terms, which add up to the total time:

  • witness — re-running the model forward pass (4 passes). Dominates in production: 57%.
  • streaming — row encoding (NTT) and Merkle hashing.
  • quad — checking quadratic constraints (Freivalds, LogUp).
  • lin — checking linear constraints.
  • overhead — a fixed per-row cost (~22 µs). At 400B it is 0.4%, but on toy models it is what holds the floor.

The field is not a free input: BabyBear is possible only if the accumulator width b fits in 31 bits. Below — the same dependencies as a graph; a formula on every node, color = role.

How it works — and where the dependencies come from

What is being proved. The GPU owner (the “prover”) convinces a checker (the “verifier” — e.g., a contract inspector) that they honestly ran a specific model on a specific input — while revealing neither the model weights nor the tokens. Exactly one number is public (how well the output is “explained” by the permitted model). This is a zero-knowledge proof: the verifier is convinced of honesty but learns nothing else.

Step 1 · Witness — the whole run becomes numbers

Every intermediate value of the run (outputs of all matrix multiplications, softmax, SiLU, normalizations) is mapped to an integer in a finite field F — a set of p ≈ 2⁶⁴ numbers where addition and multiplication wrap around (mod p). This long list of numbers is the witness — it is its correctness that gets proved. For a 400-billion-parameter model it weighs ~7.5 TB.

Step 2 · Constraints instead of element-by-element checking

The prover cannot be trusted, so one must check that the witness really came from an honest run. That is expressed as a list of constraints. A matrix product C = A·B cannot be checked element by element (that is m·n·k equalities — unaffordable), so one uses the randomized Freivalds test: instead of the whole matrix, compare one random projection λ·C·ρ = λ·(A·B)·ρ — if C is forged, the projection almost surely disagrees. Ranges and tables (softmax, SiLU) are proved with LogUp. Hence the counters Q (quadratic constraints) and L_lin (linear ones).

Step 3 · Ligero — encoding and selective opening

The witness is laid out in rows. Each row is encoded as a Reed–Solomon codeword: build a polynomial and evaluate it at N = ρ·K points (i.e., add ρ=4× redundancy). The point of the redundancy: if the prover lied anywhere, the error “smears” over a noticeable fraction of columns. The columns are hashed into a Merkle tree, and its single root pins the entire witness. Then all constraints are folded into a few short test polynomials with random coefficients, the verifier names T random columns, the prover opens them with their Merkle paths, and the verifier checks consistency. Row encoding is an NTT (same as FFT, but in the field); the cost of one cell is c(n).

Step 4 · Four rounds — why the witness is computed 4 times

The protocol is interactive and runs in 4 rounds: commit the witness → receive a random challenge → commit auxiliary data → challenge → test polynomials → challenge (which columns) → open. Every commitment happens before the next challenge — otherwise the prover would fit the witness to a challenge it has already seen (that is what soundness rests on). But the witness is needed in every round, and there is nowhere to keep 7.5 TB — so it is recomputed all 4 times. These 4 forward-pass recomputations are the most expensive part (~57% of the time), and GPU-softmax and spill attack exactly them.

Where this leads in the dependencies (what the graph shows)

  • WITNESS = 4 × forward-pass time. Grows with model size and context length (softmax — quadratic in length).
  • STREAMING — NTT encoding + Merkle hashing; grows with the row count (W/ELL) and the NTT cost c(n).
  • QUAD / LIN — the cost of checking quadratic and linear constraints (from the Freivalds and LogUp tests).
  • OVERHEAD — a fixed kernel-launch/dispatch cost per row (~22 µs). The asymptotics above do not see it, so on toy models it is what holds the floor; at large scale it saturates (the GPU is full) and becomes negligible. The only term whose share shrinks as the model grows.
  • The field holds two conditions at once: values must not overflow |F| (needs ≥ b bits) and soundness requires the field to be much larger than the column and query counts (|F| ≫ N, M). That is why a small field (BabyBear) fails at scale — it is soundness that collapses, not overflow.
  • Soundness: by opening T random columns the verifier catches cheating with probability (1−1/ρ)^T. Larger T → sounder, but the proof and its verification get heavier.

Master cost formula

PROVE_s = η · [ P · T_wit ] ← WITNESS (P = 4 passes) + (η / 10⁹) · [ (W_p/ELL)·(2·enc + 4K·c(2K) + (N/8)·h) + (W_w/ELL)·(enc + 4K·c(2K) + (N/8)·h + enc/wl) ] ← STREAMING · enc = K·c(K)+N·c(N) + (η / 10⁹) · (Q/ELL) · τ · 2K·c(2K) ← QUAD + (η / 10⁹) · β · L_lin ← LIN + 22 µs · min(m_total, 5·10⁶) ← OVERHEAD (per-row dispatch)
η = 1 / (1 − E) ≈ 1.047 — proving overhead (E = 0.045). The first four terms are asymptotics (c(n)·size); they are right at large scale but understate the floor 2–6× on toy models, because they ignore the fixed launch cost of every row. The fifth term, OVERHEAD (≈22 µs/row, derived from 39 saved runs), is exactly that cost: it dominates the floor at toy scale and saturates once the GPU is full (≈5M rows), so at 400B it is only 110 s (0.4%). floor+overhead lands within ±30% of the measured floor across the whole range.

The demonstrated run — floor+witness = 28 668 s; overhead (per-row dispatch) adds 0.4% at this scale. On a toy model (m_total ~340k) exactly this term contributes 7.5 s of the ~9.6 s measured floor — there it is the main one.
Verification soundness (§5.4) = −log₂ε, binding — the weakest term: ε = min[ (1−1/ρ)ᵀ · N/|F| · (M+T+1)/|F| ] (IRS · field · LogUp). Default T=40, ρ=4, |F|=2⁶⁴ → 16.6 bits (binding IRS). ↑T → sounder, but proof and verify grow. BabyBear (|F|=2³¹) wrecks field/LogUp at M≈10¹⁰ — that is why a small field fails at scale on soundness, not just the accumulator.

Master cost formula — after projection

There is an optimization — projection of the MoE matmuls (RoutedProjected-MoE), detailed here: routed-projection-note.

PROVE_s′ = η · [ 5 · T_wit^act ] ← WITNESS: 5 active sweeps (5-round transcript with phase 3); active-model forward, not all experts + (η / 10⁹) · [ (W′_p/ELL)·(2·enc + 4K·c(2K) + (N/8)·h) + fold_qlin(W_w) + open(W_w) ] ← STREAMING: W′ = 0.107·W; weights are not streamed — persistent q_lin fold + ledger openings + (η / 10⁹) · (Q′/ELL) · τ · 2K·c(2K) ← QUAD: Q′ = 0.245·Q + (η / 10⁹) · β · L′_lin ← LIN: L′ = 0.191·L + 22 µs · min(m′_total, 5·10⁶) ← OVERHEAD: m′ = W′/ELL — falls with the witness
W′ = 95.21G = 10.72% W (×9.33) L′_lin = 31.06G = 19.15% L (×5.22) Q′ = 42.39G = 24.49% Q (×4.08) T_wit^act — forward of the active model only (top-1 routes) 5 sweeps — R1 · R2 · R3(p3) · tests · openings fold_qlin / open — persistent weights instead of flat commit
